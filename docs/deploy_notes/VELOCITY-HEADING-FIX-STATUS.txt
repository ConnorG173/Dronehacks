Cause addressed:
The adapter replaced geometric yaw with atan2 of the final velocity setpoint.
At low speed, position corrections or inverse-model braking can point backward
even though the desired route direction is forward. Heading pacing then changed
that same velocity vector, creating a feedback loop between turning and stopping.
The fixed controller keeps yaw feedback and yaw-rate feedforward tied to the
same geometric tangent. Sideways/backward corrective velocity is not treated
as an instruction to rotate the camera.

Changes:
- Initial alignment publishes a fixed position plus bounded absolute yaw,
  through the existing pose interface. Limits are 45 deg/s and 90 deg/s^2.
  It requires 0.2 s with heading error <=5 degrees, horizontal speed <=0.15 m/s,
  measured yaw-rate magnitude <=5 deg/s, position error <=0.15 m, and a completed
  commanded turn before transitioning to velocity control.
- Initial alignment and subsequent heading waits abort after 12 s if alignment
  fails. The caller holds the latest actual position and does not auto-resume.
- Course yaw stays on the path tangent. The 5–10 degree heading pacing remains;
  exceeding 10 degrees freezes path progress and ramps velocity toward zero.
- Normal velocity changes are limited to 1 m/s^2 in 3D and 0.5 m/s^2 vertically.
  Fence/altitude guards and fault stops can override those command slew limits.
- Inverse-lag feedforward includes the changing-clock acceleration v_ref*tau_ddot.
  The 0.55 s lag and 0.10 s delay remain unmeasured assumptions.
- New API diagnostics and ROS phase-transition logs include desired/measured
  heading, heading error, measured yaw rate, alignment/wait time and command mode.
- The dashboard's owned velocity_tracker.py contains the adapted pure tracker.
  The installed alt_tracker package remains unchanged; provenance is recorded in
  VELOCITY-TRACKER-PROVENANCE.json. An old dashboard caller rejects the new adapter
  rather than silently omitting its absolute-heading command.
