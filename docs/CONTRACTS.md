# Shared contracts (both sessions read this first)

Two workstreams build in parallel: **localization** and **path streaming + following**.
This file is the only thing they share. Change it only with both sides agreeing.

## The drone you are writing for (drone 12, `skybeta-12`)

- Your code runs as ROS 2 Humble nodes in `~/team_ws/src` on the Jetson Orin Nano. This repo is
  cloned there. Never edit `~/skybeta` (organizer stack); updates refuse if you do.
- Already running (organizer stack, docker container `skybeta-stack`):
  - cuVSLAM stereo odometry → `/visual_slam/tracking/odometry` (`nav_msgs/Odometry`, ENU, frame `odom`, ~30 Hz).
    IMU fusion is **off**. It is also what PX4's EKF2 uses for horizontal position.
  - Cameras: `/oak/{left,right}/image_raw` and `image_mono`, 1024×640 @ 30 Hz, unrectified
    (`rational_polynomial`), plus `/oak/imu/data`. **No depth topic is published today.**
    If you need depth, compute it (GPU stereo) or ask the organizers how to enable on-camera depth.
  - Downward rangefinder → PX4 height. You do not see it on ROS except through PX4 topics.
  - `skybeta_flight_interface`: the only way to command PX4. You publish
    `/skybeta/setpoint/twist` (ENU velocity + yaw rate) or `/skybeta/setpoint/pose` (ENU position + yaw).
    It sends PX4 **either** position **or** velocity at 10 Hz, never both, no acceleration.
    Params you may set at launch: `setpoint_rate_hz` (10), `max_speed_mps` (1.5), `max_altitude_m` (3.0).
- A safety pilot arms and switches to Position; the interface then enters Offboard once.
  If VIO is lost mid-flight PX4 drops to Altitude and Offboard never returns until re-armed:
  **losing tracking ends the run.**

## Frames

| Frame | Meaning |
|---|---|
| `map` | The planner's course frame (`planner/README.md` "Frames"): metres, right-handed, z up, origin = centre of the 20 × 20 ft cage floor, x = east. Launch mark ≈ (-2.51, 0.91). |
| `odom` | cuVSLAM's frame. Origin = where the stack started (drone sitting on the launch mark). Drifts. |
| `base_link` | Drone body, FLU. |

At start, `map → odom` = the launch pose (`StartPos`, `StartHeadingDeg` in the course config).
Localization's job is to keep `map → odom` correct as `odom` drifts. Path following plans in `map`
and converts to `odom`/ENU for setpoints, so drift correction never touches PX4 or the organizer stack.

## Topics

| Topic | Type | Owner | Notes |
|---|---|---|---|
| `/team/odom_map` | `nav_msgs/Odometry` | localization | Pose in `map`, twist in `base_link`. ≥ 30 Hz, low latency (republish every VIO message with the latest correction). Covariance filled. |
| TF `map → odom` | tf2 | localization | Same correction as above. |
| `/team/loc/status` | `diagnostic_msgs/DiagnosticStatus` | localization | `OK` / `WARN` (degraded, e.g. VIO quality low) / `ERROR` (lost). Path following slows on WARN. |
| `/team/plan/path` | `nav_msgs/Path` | path following | Full planned path in `map` (for RViz/Foxglove and debugging). |
| `/team/mission/state` | `std_msgs/String` | path following | `idle`, `takeoff`, `course`, `landing`, `landed`, `return`, `done`, `abort`. |
| `/skybeta/setpoint/*` | see above | path following | Only path following publishes setpoints. |

Fallback so neither side blocks the other: until localization publishes `/team/odom_map`,
path following uses `/visual_slam/tracking/odometry` plus the static launch pose as `map → odom`.

## The map (already in the repo: `planner/`)

The published layout is the map (allowed by rule 6.4). Source of truth:

- `dronehacks-course-v3.step`: the organizers' course CAD (mm, z up).
- `planner/maps/course_v3.bin`: occupied surface points in the map frame (DHMAP format,
  `planner/README.md`), made by `planner/tools/cad_to_map.py`. Localization can register against
  these points directly, or rasterize a 2D slice at flight height.
- `planner/config/course_v3.yaml`: start pose, ordered checkpoints, goal, limits. The checkpoint list
  is a proposal read off the CAD; check it against the official checkpoint lines on the challenge page.

Code must work on **any** map + config in these formats: no course-specific numbers in code
(generality score + AI code review, rule 9.5). Derived maps (2D grids etc.) are generated by scripts,
never hand-edited.

## Rules that bind code (full rulebook on the challenge page)

- Everything runs on the drone (5.4). Laptop is read-only monitoring.
- No data from one run may feed a later run (6.4): no saved cuVSLAM maps, point clouds or splats from
  the course. Preloaded maps from the published layout are fine. Tuning from what you learned is fine.
- Stay below 68 in (1.727 m) except on the return (7.7). Fly ≤ ~1.2 m by default.
- Don't change PX4 safety settings, the doctor, the status agent or Tailscale (organizer rules).
- Credit every library you use in the top-level README (9.1).

## Sim

Two simulators exist; use both for different things.

- **Our Gazebo sim on GCP** (`docs/SIM.md`): Gazebo Harmonic + PX4 v1.16.2 SITL (the drone's firmware)
  + the organizers' own `skybeta` stack container, so cuVSLAM and **the same flight interface as the
  drone** are in the loop. Anyone can run it in parallel. Ground truth: `/sim/ground_truth/odom`.
- **The organizers' cloud lab** (this repo's `AI_CONTEXT.md`): Sky Beta in the prepared course, ROS 2
  Jazzy, its own companion code (`refnav/`, `onboard/`) that talks to `/fmu/in/*` directly, one
  teammate in control at a time. Good for visual realism; it does not run the drone's flight interface.

Every change is tested in sim before net time.
