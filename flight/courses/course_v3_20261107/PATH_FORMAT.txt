course_v3 path.bin - what it is and how to use it
===================================================

WHAT THIS IS
------------
A time-sampled flight trajectory for the DroneHacks course v3
(dronehacks-course-v3.step), generated by planner/ (GCOPTER) from
planner/config/course_v3.yaml on 2026-11-07.

Route (proposal read off the CAD, not an agreed rule set):
  launch mark -> hover 1.0 m -> maze gap M1 -> M2 -> M3 -> through the oval tube
  -> C2a window -> stop 1 m above the landing pad.

Planner summary for this file:
  total time      13.929 s, 1394 rows at 0.01 s
  max speed       2.43 m/s
  max tilt        20.0 deg
  max body rate   0.46 rad/s (yaw excluded)
  max yaw rate    90 deg/s
  checkpoints     M1 t=2.39 s, M2 t=4.74 s, M3 t=7.12 s, tube t=9.32 s, window t=11.79 s
  clearance       never enters an occupied voxel (0.1 m grid); 17.5% of the time
                  it is within the 0.3 m obstacle inflation margin (tight maze gaps).

FILE LAYOUT (little-endian)
---------------------------
  offset  type               value
  0       char[8]            "DHPATH\0\0"
  8       uint32             version = 1
  12      uint32             columns = 12
  16      uint64             rows R  (= 1394 here)
  24      float64            dt = 0.01 s
  32      float64[R][12]     one row per sample, columns below

  Columns, in order:
    0  t         s       time from trajectory start
    1  x         m       position, PX4 local NED
    2  y         m
    3  z         m       (negative = up)
    4  vx        m/s     velocity, NED
    5  vy        m/s
    6  vz        m/s
    7  ax        m/s^2   acceleration, NED
    8  ay        m/s^2
    9  az        m/s^2
    10 yaw       rad     heading, NED (clockwise from local +x), in [-pi, pi]
    11 yaw_rate  rad/s

  Rows are at t = 0, dt, 2dt, ... plus a final row at exactly the total duration
  (so the last gap can be shorter than dt). File size = 32 + R*12*8 bytes.

FRAME
-----
PX4 local NED with the origin ON THE PAD (on the ground at the launch mark):
  +x = the direction the drone faces on the pad
  +y = right of that
  +z = down
The planner assumed the drone sits on the launch mark facing map +x (east, into
the maze), StartHeadingDeg = 0. If the real launch heading differs, change
StartHeadingDeg in course_v3.yaml and re-plan; the follower's pad_heading_deg
must equal it.

  First row: t=0, at rest at (0, 0, -1.0), yaw 0   -> 1 m above the pad.
  Last row:  t=13.929, at rest at (0.472, 1.707, -1.0), yaw -2.10 rad
             -> 1 m above the landing pad.

The trajectory does NOT include takeoff or landing. Take off and settle at
(0, 0, -1.0) yourself, play the rows, hold the last row, then land.

HOW TO LOAD IT
--------------
Python:
    import numpy as np
    raw = open("path.bin", "rb").read()
    assert raw[:8] == b"DHPATH\0\0"
    rows = np.frombuffer(raw, "<f8", offset=32).reshape(-1, 12)
    t, pos, vel, acc = rows[:, 0], rows[:, 1:4], rows[:, 4:7], rows[:, 7:10]
    yaw, yaw_rate = rows[:, 10], rows[:, 11]

path.csv (same folder) is the identical table with a header line, for
plotting or spreadsheets.

HOW TO FLY IT
-------------
Each row maps directly onto px4_msgs/TrajectorySetpoint:
    position     = [x, y, z]
    velocity     = [vx, vy, vz]
    acceleration = [ax, ay, az]
    yaw          = yaw
    yawspeed     = yaw_rate
Publish at >= 50 Hz in offboard mode, picking the row for the current path time
(interpolate between rows or take the nearest). Positions are relative to the
pad, so if PX4's local origin is not exactly the pad, transform first (the
localizer does this in localizer/core/frames.py pad_init).

Using the team code: copy this file over
    localizer/data/course_v3_path.bin
The localizer loads it and plays it on a lag-governed clock (slows down when the
drone falls behind) and holds the last row at the end. Run the localizer tests
afterwards: they pin the old committed path (peak speed 2.42 m/s), so some may
need their expected numbers updated.

CAVEATS
-------
- Vehicle parameters in course_v3.yaml (mass, thrust range, drag) are
  placeholders from GCOPTER's demo quad, not our drone. Speed/tilt numbers are
  modest, but feasibility on the real drone is not proven.
- Mission order, checkpoint boxes and the launch heading are ASSUMED from the CAD.
- The planner is randomized (RRT with a time limit): re-running gives a slightly
  different path. This file is one validated run.
- Test in sim and check tracking error before hardware. Get team approval
  before arming.
